# ЧГК answer cards & jury scanning — Specification

Status: draft v1 (2026-10-29)

## 1. Goal

Automate result collection for in-person sport ЧГК:

1. Print answer cards (Letter paper, cut into cards). Each card carries a question
   number and a QR code identifying *tournament + team + question*.
2. After each question, the jury scans every returned card with an iPhone, marks it
   ✓ / ✗ / ?, and a photo of the card is saved.
3. Results land in a Google Sheet (one per tournament), with live standings,
   per-question stats and a projector view.

## 2. Domain parameters

| Parameter | Typical | Range |
|---|---|---|
| Rounds (N) | 3 | 1–8 |
| Questions per round (K) | 12 or 15 | any; may differ per round |
| Teams | 3–25 | design for ≤ 100 |
| Jurors scanning at once | 1 | data model ready for several (UI later) |

Question numbering is **continuous** across the game (1…ΣK). The round is shown
small on the card as «Тур 3».

No Google Cloud project is needed: a single Apps Script web app runs under a Gmail
account of the organizer's choice, and it is the only component that touches
Sheets/Drive.

### 3.1 Google account is switchable

The user must be able to move to a different Gmail account at any time, so nothing
is tied to one account.

- **Nothing in the repo names an account.** The Apps Script source is in
  `apps_script/`. Deploying it under any Gmail account (via `clasp`, which supports
  several logged-in accounts, or by copy-paste) gives a new *backend*: a `/exec` URL
  plus an admin token. The token is generated by the script's setup function and kept
  in that script's Script Properties.
- **Backends are local, named profiles**, never committed. They live in
  `~/.config/chgk/backends.json`:
  ```json
  {"active": "club", "profiles": {
     "personal": {"url": "https://script.google.com/macros/s/…/exec", "admin_token": "…", "account": "me@gmail.com"},
     "club":     {"url": "https://script.google.com/macros/s/…/exec", "admin_token": "…", "account": "chgk.club@gmail.com"}}}
  ```
  Commands:
  - `chgk backend add <name> --url … --token …`
  - `chgk backend use <name>`
  - `chgk backend list`
  - `chgk backend check` (pings it and shows which account it runs as)

  `account` is only a label for the organizer.
- **Each tournament remembers its backend.** `chgk new` copies the active profile's
  URL into the tournament's `state.json`. Switching the active profile affects only
  tournaments created afterwards; existing tournaments keep working against the
  account that holds their Sheet and photos.
- **Phones follow the tournament, not a build.** The jury link carries the backend
  URL (§7.4), so the scanner app on GitHub Pages never needs rebuilding for another
  account.
- **Printed cards don't depend on the account.** QR codes hold only the scanner URL
  and card ID (§6), so cards stay valid whichever account runs the backend.
- Moving an *existing* tournament's Sheet and photos to another account is out of
  scope for v1. Later: `chgk export` / `chgk import`.
- Step-by-step guide: `docs/google-account.md` (Phase 2).

## 4. Tournament configuration (Python, not YAML)

Each tournament is a folder `tournaments/<slug>/` with a `config.py` written by the
organizer:

```python
from datetime import date
from chgk.config import Tournament, CardFields, Layout, LogoMode

tournament = Tournament(
    slug="autumn-cup-2026",
    name="Осенний кубок",
    date=date(2026, 11, 15),
    rounds=3,
    questions_per_round=12,          # int, or a list per round: [12, 12, 15]
    scanner_url="https://<user>.github.io/qa-chgk/s/",   # printed inside every QR
    spares_per_team=3,               # unnumbered spare cards per team, whole game
    card=CardFields(
        team_name=True,
        tournament_name=True,
        date=True,
        logo=LogoMode.TEAM_ELSE_TOURNAMENT,   # NONE | TEAM | TOURNAMENT | TEAM_ELSE_TOURNAMENT
        tournament_logo="logos/tournament.png",
        logo_grey=0.12,
    ),
    layout=Layout(cols=3, rows=5, qr_size=0.65),   # 15 cards per Letter page
)
```

Values the system generates (tournament ID, spreadsheet ID, jury token) are stored
next to the config in `tournaments/<slug>/state.json`, which is never hand-edited
and is git-ignored because it contains secrets. Teams are in `tournaments/<slug>/teams.py`,
Python like config.py (user request, replacing teams.csv):
`teams = [team("42", id="645", logo="42.png"), team("Звезды сошлись"), …]`.
Given team IDs are kept (upper-cased); missing ones are assigned and written back (the
file is then regenerated). `chgk teams` regenerates it from the Sheet's Teams tab.
`tournaments/example/` is a working example.

## 5. Google Sheet (one spreadsheet per tournament)

Created by `chgk new`. Tabs:

| Tab | Who writes | Content |
|---|---|---|
| **Settings** | CLI | name, date, rounds, questions per round, IDs |
| **Teams** | organizer (source of truth) | `team_id` (the organiser's own, e.g. the rating.chgk.info number `58746`, used as given; blank → assigned `A01`, `A02`, …; 1-8 digits or capital Latin letters, unique, stable), `name`, `city`, `logo_file`, `logo_prompt` |
| **Log** | Apps Script, append-only | `scan_id` (UUID, idempotent), server time, client time, juror, device, team, question, status, photo link, source (`app` / `sheet`) |
| **Итоги** (first tab) | formulas | standings: each team's round sums, Итого, Место. A shared place reads «2-3» (user request), a single one is a number. Rows sorted by Итого; on a tie the better last round is higher, then the round before, …, then team ID (user rule; the place stays shared). Round sums are looked up by team ID, so sorting a round tab is harmless. Round columns share their round's colour. Team names are plain text, left-aligned (a team called «42» must not become a number) |
| **Тур 1 … Тур N** | Apps Script + jury edits | one tab per round (user request): teams × that round's questions (continuous numbers) and «Сумма», sorted by «Сумма» (equal sums in team ID order). Narrow question columns; tab and header coloured, alternating by round |
| **Stats** | formulas | per question: number of teams that took it, % |

### Cell values on the round tabs

| Value | Meaning | Counts as |
|---|---|---|
| *(blank)* | no card received | 0 |
| `R` | card received (scanned), not judged yet | 0 |
| `1` | correct ✓ | 1 |
| `0` | incorrect ✗ | 0 |
| `?` | to be decided | 0 until resolved |

A missing card scores as incorrect, but the sheet always shows whether a card was
**received** (blank vs `R`/`0`/`1`/`?`).

### Rules
- **Last scan wins**, decided by the client timestamp of the action, so an offline
  scan synced late does not overwrite a newer decision. Every action stays in Log.
- The jury resolves `?` and appeals **by editing the mark cell on the round tab**. An
  `onEdit` trigger records those edits in Log (`source = sheet`) with a timestamp, so
  they take part in last-write-wins.
- Tabs are re-sorted after every change, so rows move. Jury edits are therefore found by
  comparing every mark with the last value the backend knows (hidden Meta tab), by team
  ID, never by the edited row. Every batch from the phones runs the same check first, so
  a jury decision is time-stamped before a late-synced older scan is compared with it.
- Writes are serialized with `LockService`, which keeps several simultaneous jurors
  safe.

## 6. QR code and card identity

- QR content is a URL, so the iPhone's built-in Camera also opens the app:
  `https://<user>.github.io/<repo>/s/#<TID>.<TEAM>.<Q>`
  - `TID`: random 5-char tournament code; `TEAM`: `team_id`; `Q`: question number,
    or `S1…Sn` for spare cards.
  - Example: `…/s/#K7M2Q.A07.27`. This is short enough for a small, robust QR
    (error correction M, quiet zone 4 modules). Printed at **0.65″** including the
    quiet zone (user's choice from the test print; configurable).
- The QR contains no secret. Submitting a mark requires the jury token (§7.4).
- A numbered card's mark always goes to the question in its QR code. Only when a
  **spare card** is scanned (no number in its QR) does the app ask the juror, right
  then, which question it is: «Запасная карточка — какой вопрос?» with a number pad
  for the number the team wrote in the box, and the current question (§7.1) as one
  quick button. Nothing is recorded for that card until the juror answers (user rule).

## 7. Scanner web app (iPhone, GitHub Pages)

Static HTML/JS (ES modules, no build step), installable to the Home Screen. Camera
access needs HTTPS, which GitHub Pages provides.

### 7.1 Flow (the only mode in v1)
1. The **current question follows the scans** (user decision, replacing a manual
   picker): the first numbered card of a later question makes it current, shown in big
   digits at the top. The juror never has to set it; ◀ ▶ can still change it by hand.
   It is used only for spare cards, the "missing" list and the warnings below; every
   numbered card is marked for the question in its own QR code.
2. The camera scans continuously. When a card is detected:
   - a full-resolution **photo of the frame is captured** (every card);
   - the team name is shown in large type and a `received` event is recorded;
   - **warning** (colour + vibration) if the card is from an earlier question than the
     current one («Карточка вопроса 5 (идёт 7) — отмечено для 5»; the mark still goes
     to 5), or if this team already has a mark for this question.
3. The juror taps **✓ / ✗ / ?**. The status event is recorded and the app returns to
   scanning.
4. **"Missing: n teams ▸"** lists teams with no card for the current question
   (local state merged with server state).
5. **«Чья карточка?»** (user request): a read-only mode. The camera keeps scanning and
   each card is only described — team name and ID, question and round (or the spare
   number), and the mark it already has; another tournament's card, an unknown team or
   a jury/board QR are named as such. Nothing is recorded and the current question
   doesn't move. Before setup, scanning a card shows what its QR holds (team ID,
   question, TID).

### 7.2 Sync
- Internet is usually fine, but every event goes to an on-device queue (IndexedDB)
  first and is posted from there with automatic retry. A status pill shows
  "synced / n pending".
- Photos upload separately from marks (JPEG ≈ 150 KB), so a slow photo never delays
  a result.
- Events are idempotent (`scan_id`), so retries never double-count.
- Measured (spike 1): one Apps Script request takes ~1 s, and a photo with the Drive
  save ~3 s. So marks are sent in batches (all pending events in one request), and
  photos upload 2–3 at a time.

### 7.3 Multi-juror readiness (UI later)
Every event carries juror name, device ID, client timestamp and UUID, and the
missing list is backed by the server. Adding several jurors later needs UI work
only, not data-model changes.

### 7.4 Access
- v1: **secret jury link**. `chgk jury-link` prints a URL and a QR. The link carries
  the tournament's backend URL, its TID and the jury token. Opening it once stores
  them on the phone, which is what lets a tournament run on any Google account
  (§3.1).
- Later option: Google sign-in with an allow-list of emails.
- Caveat: on iOS a Home-Screen app and Safari keep separate storage, so a card URL
  opened from the built-in Camera may ask for the jury link once.

### 7.5 The juror does **not** see the official answer
The app doesn't show it (decided).

## 8. Answer cards (PDF)

### 8.1 Page and card
- Letter (8.5″×11″), printed at 100%, so it's safe to send to a copy shop. The 0.25″
  margins cover printers that can't print to the edge.
- The grid is configurable; the default is **3 columns × 5 rows = 15 cards**, about
  2.67″ × 2.1″ each.
- Cards sit edge to edge, so neighbouring cards share one cut line and no paper is
  wasted. Thin grey cut lines; crop marks in the margin for the guillotine modes.

### 8.2 Card contents (Russian labels; no «Вопрос»)
```
┌───────────────────────────────┐
│ 27                ▄▄▄▄  Тур 3 │   big question number; QR top-right
│                   █▀▀█        │
│                   ▀▀▀▀        │
│   (pale logo watermark)       │   writing area
│                               │
│ Синие зайцы · Осенний кубок · 15.11.2026 │   optional footer
└───────────────────────────────┘
```
- Spare cards have no words: an empty box sits where the question number goes, and the
  team writes the number in it.
- Characters the font can't draw (e.g. emoji in a team name) print as `?`, with a
  warning.
- An embedded Unicode TTF font (OFL licence, e.g. PT Sans or Noto Sans) is used for
  Cyrillic.
- The logo never overlaps the QR quiet zone.
- Logo watermark default: **12% grey**, configurable. This is the ink of the logo's
  dark parts (its darkest 10%), not of a single darkest pixel; see §9. The user
  first chose 3% from solid swatches, saw the real logos far too faint, and picked
  12% from a side-by-side of real cards.

### 8.3 Imposition: all three modes are available, and the CLI **asks which one** before generating unless it's passed
| Mode | Description |
|---|---|
| `team-pages` | each page holds one team's cards in order; leftover slots become extra spares |
| `cut-stack` | for guillotine: stack all sheets, cut once; stacking the piles in slot order gives every team's cards already sorted |
| `scissors` | one team per page, same edge-to-edge grid (cards share cut lines, no wasted paper); darker dashed lines and no crop marks |

### 8.4 Distribution
Each team gets **one stack for the whole game** (numbered cards + spares).

### 8.5 Test page
`chgk test-page` prints a calibration page:
- the logo at several grey shades, so the organizer can pick one that stays pale on
  the actual printer;
- QR codes at several sizes;
- a 1″ ruler, to confirm the page printed at 100%.

### 8.6 Jury printout (Russian)

Every `chgk cards` run also writes the jury sheet, `out/<slug>/jury.pdf`, as a
separate file so the secret never ends up on team cards. It's also available alone
as `chgk jury-sheet <folder>`.

- **Page 1, jury only** (user request): QR codes for the secret jury access (§7.4,
  framed, marked secret), the Sheet with edit rights, and the scanner, side by side.
  Only this page's footer says «секретно».
- **Page 2, no secrets** (user request): QR codes for the projector board and the
  **view-only Sheet** (`…/htmlview`; the backend shares every new Sheet as "anyone with
  the link can view", `chgk view` does it for older ones). It may be shown to teams;
  the view-only Sheet shows marks as soon as they're entered, the board only after a
  round is revealed. A link that doesn't exist yet gets a dashed empty box.
- **Page 3:** tournament name, date, rounds × questions, teams (+ reserve decks), TID;
  the links as text (no QR codes) with the backend profile and Google-account label;
  juror how-to; «?» and appeals how-to; how to handle a team that turns up
  unregistered (when reserve decks exist).
- **Team forms** (user request; replaces the old roster): one per team with only the
  ID and name, then 8 numbered lines for the players' names, two forms per row. Blank forms for the
  reserve decks (R1, R2, …) with a «Название команды:» field. Handed to the teams.
- **Then a paper backup grid,** for when phones or internet fail: one block per round
  (teams × questions + a «Сумма» column), then an «Итого» block (teams × rounds +
  total). Reserve decks get rows with a blank name.

### 8.7 Teams that turn up unregistered (reserve decks)

- `reserve_teams` in config.py (default 2, 0–9): full card decks R1, R2, … printed
  with every `chgk cards` run. No team name (with team names on cards, a «Команда:»
  line to write it on), no logo of their own (tournament logo, else `nologo.png`).
  A registered team may not use these IDs.
- The backend knows them from the start (Teams tab, `reserve` column) but keeps them off
  «Итоги», the round tabs and Meta, so an unused reserve never shares last place.
- The first valid scan of a reserve card adds the team to every tab as
  «R1 · впишите название». The jury types the real name over it on «Итоги», a round
  tab or Teams, and the name is copied to every tab (matched by team ID). Naming a
  reserve team on Teams before its first scan adds it too.
- Any team can be renamed this way; a cleared name cell is put back. `chgk teams`
  leaves reserve teams on the backend (they are not written to teams.py).
- Jury link format: `<scanner_url>#setup=<TID>.<JURY_TOKEN>.<DEPLOYMENT_ID>`. It's
  encoded in Python, will be decoded by the JS scanner, and has shared test vectors in
  `tests/vectors/jury_links.json`.

## 9. Logos

**Shared logo library:** `logos/` at the repo root (user decision, 2026-10-29).
- A logo name (`logo=` in teams.py, `tournament_logo`, `fallback_logo`) is looked
  up in the tournament folder first, then in `logos/`, so one team logo serves every
  tournament.
- Team logos in `logos/` are **private**: git-ignored, local only. Only
  `logos/nologo.png` (the fallback owl) is in the public repo.
- **Fallback chain** per card: team logo → tournament logo (if the mode uses it) →
  `fallback_logo` (default `nologo.png`) → none. `LogoMode.NONE` disables logos
  entirely.
- A logo file that can't be found prints a warning and the card uses the next
  fallback. A fresh clone without the private logos still prints, with owls.
- Logos are downscaled to 600 px before embedding, which keeps PDFs small.
- **Size:** `CardFields.logo_size` (inches). `None` (the default) fits the logo into
  the writing area. A number makes it a square centred in the full card height, left
  of the QR column, behind the number and footer text but never behind the QR, and
  shrunk to fit. On a 3×5 card the maximum is about 1.85 in.
- **Shade:** the darkest 10% of the drawing gets exactly `logo_grey` ink, and anything
  darker is clamped. Scaling by the single darkest pixel printed the user's light-grey
  logos at about a third of the chosen shade (fixed 2026-10-29).

A pale greyscale watermark. The source is chosen per team and per tournament:

| Source | How |
|---|---|
| none | no logo |
| provided file | PNG/JPG/SVG in `tournaments/<slug>/logos/` → greyscale → flatten → lightened to the chosen shade |
| Claude-drawn SVG | vector emblem or monogram from a text spec (drawn in a Claude Code session, or via the Claude API with the user's key) |
| image API | prompt → OpenAI / Google image model (user's API key) → same post-processing |

The Claude API does not output raster images, but it can write SVG.

### 10.1 Projector board (user decisions)
- A web page next to the scanner (`…/b/`), opened on the projector laptop from the board
  link (QR on page 2 of the jury sheet, or `chgk board`). Read-only: its board token can
  read teams and marks but nothing else, and is separate from the jury token.
- **Shown only after each round.** Nothing appears until the person at the projector
  presses → (or space, or «Показать тур N»); each press reveals the next round, ← takes
  the last one back. Totals, order and places use only the revealed rounds, so marks
  already coming in for the next round never leak. The page refreshes every 15 s, so
  appeal corrections in revealed rounds appear on their own.
- **Up to `board_grid_max_teams` teams (default 5):** the full grid of every revealed
  round (+ / − per question, «Σ» per round), then Итого and Место. **More teams:** Место,
  Команда, Итого and the grid of the last revealed round. G switches views; F fullscreen.
- A «Взяли» row under the grid: how many teams took each question.
- Order and places as in «Итоги»: Итого, then the last revealed round, the round before,
  …, then team ID; shared places «2-3». `?` and `R` show as «?» and count as 0; a
  missing card is «−».

## 11. Testing (required for every phase)

Every component has unit tests, and a phase is not done until they pass. Logic is
written as pure functions, so the code that touches the camera, Sheets and Drive
stays a thin layer.

| Layer | Runner | What is unit-tested |
|---|---|---|
| Python (`chgk/`) | `uv run pytest` | config validation and question/round numbering; QR payload encode/decode; imposition (every card placed exactly once; simulated cut-and-stack yields sorted decks; page count); layout geometry (everything inside margins, QR ≥ min size, QR and logo don't overlap); logo processing (greyscale, darkest pixel ≤ chosen shade); Apps Script client with mocked HTTP (`respx`) |
| PDF output | `uv run pytest` | smoke tests: page count; Cyrillic text extractable (`pypdf`); **QR codes decoded back from the rendered PDF** (`pypdfium2` + `zxing-cpp`) and matching the expected payloads |
| Apps Script logic (`apps_script/`) | `node --test` | last-write-wins merge, status → cell mapping, request validation, token check, idempotency by `scan_id`. Pure functions live in a file that runs both in Apps Script and in Node |
| Web app logic (`web/`) | `node --test` | payload parsing, offline queue (retry, dedupe), missing-teams computation, question-mismatch / duplicate warnings, spare-card handling |
| Cross-language contract | both | shared test vectors in `tests/vectors/*.json` (QR payloads, events, merge cases), checked by both the Python and JS suites, so the encoder and the decoders can't drift apart |

Not unit-testable, so covered by a manual checklist per release (`docs/manual-checks.md`):
- iPhone camera scanning speed and reliability;
- print scale and grey shades on real printers;
- deployed Apps Script quotas and CORS.

CI: a GitHub Actions workflow runs `uv run pytest` and `node --test` on every push,
once a remote exists.

## 12. Tech stack

- **Python ≥ 3.12, uv**:
  - `typer` (CLI), `reportlab` (PDF), `segno` (QR), `Pillow` (logos), `httpx`;
  - dev: `pytest`, `respx`, `pypdf`, `pypdfium2`, `zxing-cpp`.
- **Apps Script** (`apps_script/`): deployed once as a web app ("execute as me",
  "anyone"). The code is pushed with `clasp` or pasted by hand.
- **Web** (`web/`): plain HTML/JS with a vendored QR decoding library (`qr-scanner`
  or `zxing-wasm`, picked in the spike), served by GitHub Pages.
- **Node** (dev only): its built-in `node --test` runner, no npm dependencies.
